# Handoff: Native-feeling iOS PWA

## Task(s)
- **Not started.** Objective for the next session: make the mobile web app *feel* like a
  natively-installed iOS app once launched from the home screen, not just look branded. This
  follows directly on from the per-user PWA icon work landed in commit `665bfc593` (Kolby vs. Abby
  home screen icons, `apple-mobile-web-app-capable`/`status-bar-style` meta tags) — that work is
  done and deployed; this handoff is about the next layer: safe areas, keyboard behavior, scroll
  feel, and tap feedback.

## Critical References
- `src/app.html` — viewport meta (`viewport-fit=cover` already set), the new
  `apple-mobile-web-app-*` meta tags, inline splash-screen JS, `overscroll-behavior-y: none`.
- `tailwind.config.js:21-23` — defines exactly one safe-area utility, `pb-safe-bottom`.
- `src/lib/components/chat/MessageInput.svelte` — the bottom-fixed chat input bar; the single
  most important surface for "does this feel native," and currently has none of the safe-area or
  keyboard-visualViewport handling described below.
- `src/lib/components/common/Dropdown.svelte`, `src/lib/components/chat/ModelSelector/Selector.svelte`,
  `src/lib/components/chat/MessageInput/InputMenu.svelte` — existing, working `visualViewport`
  keyboard-aware positioning pattern. Reuse this pattern rather than inventing a new one.
- `backend/open_webui/config.py:95-115` — see Gotcha below before touching any static asset again.

## Findings from this session's research (verified via grep, nothing fixed yet)
1. **Zero uses of `env(safe-area-inset-*)`** anywhere in `src/`, despite `viewport-fit=cover`
   already being set. Content can render under the Dynamic Island/notch or flush against the home
   indicator with no compensating padding.
2. `tailwind.config.js` defines only `pb-safe-bottom` (`env(safe-area-inset-bottom)`), and it's
   used in exactly one place — a settings panel (`AdvancedParams.svelte`) — not in
   `MessageInput.svelte`, which is where it matters most.
3. **No top-safe-area utility exists at all** (no `pt-safe-top` equivalent).
4. This session added `apple-mobile-web-app-status-bar-style: black-translucent` to `app.html`.
   That makes the iOS status bar transparent and lets app content render underneath it in
   standalone mode. **Unverified**: whether the top app chrome (header/model selector) now sits
   under the status bar/notch. Check on a real device first; if it clips, add a `pt-safe-top`
   utility and apply it to the top chrome.
5. `overscroll-behavior-y: none` is already set globally on `html` — the right baseline to kill
   whole-page rubber-band bounce. Confirm it doesn't also suppress an intentional gesture
   somewhere (e.g. a pull-to-refresh, if the chat list has one).
6. `window.visualViewport` is already used for keyboard-aware repositioning, but only for floating
   menus/dropdowns — not for the message input bar. The input bar currently appears to rely only
   on the `interactive-widget=resizes-content` viewport meta (a newer spec with inconsistent
   Safari support, especially in standalone/home-screen mode). If real-device testing shows the
   input bar misbehaves when the keyboard opens, extend the same `visualViewport` pattern already
   proven in `Dropdown.svelte` rather than inventing something new.
7. **No `-webkit-tap-highlight-color` reset found anywhere.** Buttons/links likely still show the
   default iOS gray/blue tap-flash rectangle, which reads as "website," not "app."

## Gotcha (cost real time this session — don't repeat it)
`backend/open_webui/config.py:97-115` wipes every top-level file in the runtime `STATIC_DIR`
(`backend/open_webui/static` inside the container) on **every process start**, then repopulates it
*only* from the frontend build's nested `static/static/` folder at repo root — **not** from
`backend/open_webui/static/` directly, and not from the top-level `static/` folder either. Any new
file meant to be served under `/static/*` in production must go in `static/static/`, or it
silently disappears the instant the container boots, even though it was correctly baked into the
Docker image at build time. `docker exec <container> ls ...` on a *running* container reflects the
post-wipe state (the truth); `docker run --rm <image> ls ...` bypasses the entrypoint (skips
`config.py`'s wipe/repopulate) and shows misleading pre-wipe state — don't use the latter to
"confirm" a static asset shipped.

## Not yet investigated / open questions
- **Splash screen**: `app.html` already has an inline JS splash-screen implementation using
  `splash.png`/`splash-dark.png`. Unknown whether it's sufficient for the standalone-launch case
  or whether real-device testing shows a flash of unstyled content first. iOS's native
  `apple-touch-startup-image` mechanism is a separate, more device-size-specific option worth
  comparing against.
- **Haptics are not achievable** from a plain web app on iOS Safari (no Vibration API support) —
  don't spend time chasing this; it's a hard platform limitation, not a missing implementation.
- **Per-container scroll/bounce behavior** — only the global `html` `overscroll-behavior` was
  checked. Audit the actual chat message list and any modal/drawer scroll containers individually.
- **Long-press context menu / callout suppression** on custom buttons and message bubbles —
  unaudited.
- **Nothing in this list has been tested on a real iPhone.** All of it is inferred from source +
  grep. Real-device testing (ideally in actual standalone/home-screen mode, not just mobile
  Safari) should come *before* writing fixes, to confirm which of these findings are real problems
  vs. already handled some other way.

## Action Items & Next Steps
1. Launch the current build from the home screen on a real iPhone (standalone mode, not just
   mobile Safari) and screenshot the status-bar/notch area and the bottom input bar first — this
   confirms or rules out finding #4 before any code changes.
2. Add a `pt-safe-top` Tailwind utility (mirroring `pb-safe-bottom` in `tailwind.config.js`) and
   apply both insets to the real app chrome: top header/model selector and `MessageInput.svelte`.
3. Only if device testing shows `interactive-widget=resizes-content` is insufficient: extend the
   message input bar's keyboard-avoidance using the same `visualViewport` pattern already proven
   in `Dropdown.svelte`.
4. Add `-webkit-tap-highlight-color: transparent` globally, paired with a deliberate `:active`
   state so taps keep visible feedback — don't just remove all touch feedback wholesale.
5. Re-verify `overscroll-behavior-y: none` doesn't suppress a wanted gesture anywhere before
   calling scroll feel "done."
