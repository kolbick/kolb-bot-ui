## Learnings
- The cptr “invalid startup token” error was unrelated to Open WebUI OAuth. It came from cptr's independent first-admin setup flow; Cloudflare redirects can also lose the startup-token query parameter.
- cptr 0.9.15 trusted-header mode is incomplete for this topology: middleware can trust the email header, but `/api/auth` and per-route helpers expect `cptr_session`, while stock `check_access()` ignores JWT cookies in trusted-header mode. The compatibility patch creates the cookie via 307 and accepts valid JWTs in every auth mode.
- Starlette executes middleware in reverse declaration order. The bootstrap middleware must be inserted after cptr's auth middleware in source so it executes first.
- A stale cptr cookie must be replaced, not merely detected as present. Verification explicitly covers stale-cookie replacement.
- Trusted identity headers must not be accepted on publicly bound ports. Both cptr ports now bind to `127.0.0.1`; Cloudflare's local tunnel remains the public path.
- Cloudflare `cfat_` account-owned API tokens can authenticate account endpoints even when `GET /user/tokens/verify` returns 401. Test a permitted account endpoint such as `GET /accounts` before declaring such a token invalid.
- Direct container filesystem edits disappear on recreation. The tracked startup patch is mounted from the repository instead.
